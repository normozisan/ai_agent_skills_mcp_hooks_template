# モバイルアプリ開発ガイドライン(PWA / ネイティブExpo)

スマホアプリを作る場合の追加規約。要求仕様・設計・実装・テスト・リリースの全フェーズで適用する。

## 0. プラットフォーム判定(要求仕様フェーズで決定し、仕様書に明記)

| 選択肢 | 選ぶ基準 |
|---|---|
| **A. レスポンシブWeb / PWA(既定・推奨)** | ブラウザで動けば足りる場合。インストール感・ホーム画面アイコン・オフラインはPWAでカバー可能 |
| **B. ネイティブ(Expo / React Native)** | 以下のいずれかが**Must要件**のときのみ: ストア配布必須 / プッシュ通知(特にiOS) / カメラ・センサー・GPS常時利用 / 深いオフライン動作 / OSレベル連携 |

迷ったらAで作って検証し、必要になったら `/iterate` または `/promote` でBへ移行する。判定結果は仕様書に「モバイル: PWA」または「モバイル: ネイティブ(Expo)— モバイルガイドライン適用」と明記する。

## 1. A: PWAで作る場合

- 通常のWebスタック(Vite + React)+ `vite-plugin-pwa` で manifest / service worker を構成
- 仕様に含めること: インストール導線(A2HS)、オフライン時の挙動(キャッシュ方針)、iOS Safariの制約(プッシュ通知はiOS 16.4以降、ストレージ上限)
- デザイン: モバイルファースト(375px基準)、タッチターゲット44px、セーフエリア `env(safe-area-inset-*)`
- **テスト・デザインレビュー・リリースは通常のWeb手順がそのまま使える**(Playwright / Webデプロイ)。Playwrightのモバイルビューポートテストを必須にする

## 2. B: ネイティブ(Expo)の技術スタック既定値

| 領域 | 既定 | 備考 |
|---|---|---|
| フレームワーク | Expo SDK(最新安定版)+ TypeScript | ベアRNではなくExpoマネージドを使う |
| ルーティング | expo-router | ファイルベース |
| スタイル | StyleSheet または NativeWind | CSSは使えない |
| ユニットテスト | jest-expo(Vitestの代わり) | ロジックを `lib/` の純関数に分離する方針は同じ |
| E2Eテスト | Maestro(第一候補) | YAMLでフロー記述。エミュレータ/実機が必要 |
| ビルド・配布 | EAS Build / EAS Update | Expoアカウントが必要 |

最新のAPI・設定は Context7 MCP で `expo` / `expo-router` を確認してから書くこと。

## 3. ネイティブでのデザイン実装(ui-designer / implementer / design-reviewer向け)

- **デザイントークンはCSS変数が使えない**ため、`src/theme.ts`(TSオブジェクト)として実装し、全コンポーネントはそこから参照する(direct値の直書き禁止。Webの `tokens.css` に相当)
- セーフエリアは `useSafeAreaInsets` で処理。タッチターゲット44pt以上、主要アクションは親指圏(画面下部)
- プラットフォーム作法を尊重: 戻る操作(Androidバックボタン)、iOSのスワイプバック、ナビゲーションはタブ or スタックの標準パターン
- デザインプレビュー(`docs/design_preview.html`)はモバイル幅の静的モックとしてそのまま有効
- **デザインレビューの方法**: `npx expo start --web` でWeb版を起動し、Playwrightでスクリーンショット確認(近似)。ネイティブ固有の部分(画面遷移アニメーション、ジェスチャー、実機フォント)はレビュー対象外となるため、「実機確認チェックリスト」としてレビュー結果に明記し、ユーザーに実機(Expo Go)での確認を依頼する

## 4. ネイティブでのテスト(test-engineer向け)

- ユニット: jest-expo で `lib/` の純関数を網羅(境界値の定番セットは共通ガイドラインどおり)
- E2E: Maestroフローを主要ユーザーストーリー分作成。**エミュレータ/実機が無い環境では実行できない**ため、その場合は:
  1. Expo Web版に対するPlaywrightテストで近似カバー
  2. 実機でしか確認できない項目(プッシュ通知、カメラ、ジェスチャー等)を**「手動確認チェックリスト」としてテスト計画書に必ず分離記載**し、テスト結果報告書でも「自動 / 手動未実施」を区別する
- 「全テストパス」と報告してよいのは自動テストの範囲のみ。手動未実施項目を隠さない

## 5. ネイティブでのリリース(release向け)

- ビルド: EAS Build(`eas build`)。配布: TestFlight(iOS)/ Google Play Internal Testing(Android)
- **事前にユーザーへ案内すること**: Apple Developer Program(年99ドル)/ Google Play Console(初回25ドル)のアカウントが必要。登録・審査提出はユーザー自身の操作
- ストア審査に必要なもの: プライバシーポリシーURL、各権限の利用目的文言(カメラ等)、スクリーンショット、アプリアイコン
- 軽微な修正はEAS UpdateによるOTA更新の方針をリリースノートに明記
- リリースチェックリストに追加: 実機での起動確認 / 権限拒否時の挙動 / オフライン時の挙動
