# 数値ゴール駆動の改善ループ(ループエンジニアリング)

ゴールを測定可能な形で固定し、「計測 → 改善仮説1つ → 実装 → 再計測」のループを終了条件まで回す。実装済みアプリ(`app/`)が対象。

ゴール: **$ARGUMENTS**

## 1. ゴールの確定(ループに入る前に必ず)

- ゴールを**計測コマンドで判定できる形**に変換する。曖昧なゴール(「速くして」「軽くして」)はそのまま受けず、測定可能な案を提示してユーザーに確認し確定する(例: 「速く」→「Lighthouse Performance 90以上」or「トップ画面のLCP 1.5秒以内」)。
- **計測方法を先にコマンド化**する(例: `npx lighthouse`、`npm run build` のサイズ出力、`npm test` のパス率、Playwrightでの操作ステップ数計測)。計測できないゴールはループに入れない。
- 終了条件を宣言する: ①ゴール到達 / ②上限周回数(`--max-loops`、既定5周) / ③**2周連続で改善なし**(収束打ち切り)。

## 2. ベースライン計測

現状値を計測し、ゴールとの差分を記録する。既にゴールを満たしていればそのまま報告して終了する。

## 3. 改善ループ(1周 = 仮説1つ)

各周回で以下を守る:

1. **改善仮説は1周に1つ**(複数同時に変えると、どれが効いたか分からず巻き戻しもできない)
2. 実装(小さければ自分で、大きければ implementer サブエージェントに委譲)
3. 再計測し、前回値と比較
4. **改善していなければその変更を巻き戻す**(git で戻す。悪化を積み重ねない)
5. 周回ログを記録: 仮説 / 変更内容 / 計測値の推移 / 採用・巻き戻し

### ループ中のガードレール(違反禁止)

- **毎周回、既存テストを全実行**する。数値を上げるために機能を壊さない(テストが落ちたらその周回は不採用)
- **テストや計測を弱めて「達成」に見せない**(テスト削除・閾値緩和・計測条件の変更は禁止。ゴール側を変えたい場合はユーザーに確認)
- 要求仕様の受け入れ基準と矛盾する変更をしない(矛盾する場合はループを止めてユーザーに確認)

## 4. 終了と報告

`docs/08_refine_report.md` に保存する: 確定したゴールと計測方法 / ベースライン→最終値の推移表 / 各周回のログ(採用・巻き戻し含む) / 終了理由(到達・上限・収束) / 未達の場合は残る差分と、次に効きそうな打ち手。

ユーザーへの報告は「ゴール: 到達 / 未達(現在値)」を最初の1行で伝える。未達を到達と偽らない。収束打ち切りの場合は「これ以上はアーキテクチャ変更が必要」等、ループの外の選択肢を提示する。
