# POC→本番昇格フェーズ

POCの学びを引き継いで、本番品質のアプリを正式パイプラインで作り直す/育てる。

**大原則: 正式な要求仕様書(`docs/02_requirements.md`)を確定させるまで、本番の実装には一切入らない。** 仕様なしでコードだけ本番品質に変えることはしない。

ユーザーからの入力: $ARGUMENTS

## 正式仕様の入力源の決定(最初に判定)

正式仕様書の一次入力を、以下の優先順で決める:

1. **$ARGUMENTS に `--spec` がある場合**: ユーザーが用意した正式仕様書を一次入力にする
2. **`docs/poc/original_spec.md` が存在する場合**(POCが仕様持ち込みで作られた場合): その原文を一次入力にする(POC仕様は要約版なので使わない)
3. **どちらも無い場合**(POCがアイデアから作られた場合): POC仕様+POCレポート+ヒアリング結果を材料に、手順3で正式仕様を**新規作成**する

いずれの場合も、決定した入力源をユーザーに明示してから進める。

## 手順

### 1. POC結果のヒアリング

`docs/poc/00_poc_spec.md`・`docs/poc/01_poc_report.md`・`app/` を読む。$ARGUMENTS に学びが無ければユーザーに選択肢を提示して確認する:
- 検証したい仮説は確認できたか(何がウケて、何が要らなかったか)
- POCから変えたいこと・追加したいこと
- 市場調査をやるか(POCで市場性の確信があるならスキップ可、推奨は実施)

### 2. POCコードの流用判定

code-reviewer サブエージェントに `app/` を評価させる(観点: 本番の土台にできる構造か、書き直しの方が速いか)。判定結果と推奨(流用 / 部分流用 / 作り直し)をユーザーに提示して決定する。

- **作り直しの場合**: 既存 `app/` を `app-poc/` にリネームして保全する(削除はユーザー承認なしにしない)
- **流用の場合**: 以降の実装フェーズは既存コードのリファクタリング+品質ゲート通過を含むタスク計画にする

### 3. 本番パイプラインの実行

※ 各スキルの実行は、スキル呼び出し機能があればそれで行い、無い環境では該当スキルの `SKILL.md` を読んでその手順に従う。

POCの学びを引き継ぎながら、通常のフェーズを順に実行する:

1. (選択時のみ)`market-research` — POCの仮説検証結果を前提情報として渡す
2. `requirements` — 冒頭で決定した仕様入力源に応じて実行する:
   - 正式仕様がある場合(--spec または original_spec.md): `--spec` としてその原文を渡し、POCの学び・ヒアリング結果を「追加の要望」として渡す(原文とPOCの学びが矛盾する場合はユーザーに確認)
   - 無い場合: `docs/poc/` の両ファイルとヒアリング結果を入力に、正式な `docs/02_requirements.md` を新規作成
   - どちらの場合も、境界値・異常系・非機能要件をここで正式に定義し、**完成した仕様書をユーザーに提示して承認を得てから次へ進む**
3. `design` — POCの簡易トークンを参考情報として渡す(正式にアートディレクション3案から選択)
4. `implement` — 流用判定の結果をタスク計画に反映
5. `test-app` — フルのテスト設計・実行

各フェーズの完了ゲート・品質基準は本番と同一(緩和しない)。

### 4. 完了報告

POCとの差分(何が正式化・強化されたか)、品質状態、`/release` で公開準備ができることを報告する。
