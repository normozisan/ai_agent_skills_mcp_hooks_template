# 改修フェーズ(v1完成後の変更反映)

変更要求をドキュメントと実装の両方に矛盾なく反映し、既存機能を壊していないことを回帰テストで保証する。

変更要求: **$ARGUMENTS**

## 大原則

**コードだけ直してドキュメントを腐らせない。** 変更は必ず上流(仕様・デザイン)→下流(実装・テスト)の順で反映する。

## 手順

### 1. 変更の分類と影響分析

変更要求を読み、`docs/` の成果物と `app/` を確認して以下を判定する:

| 分類 | 影響範囲 |
|---|---|
| バグ修正(仕様どおり動かない) | 実装+テストのみ |
| デザイン変更 | 03_ui_design.md → 実装 → デザインレビュー |
| 機能追加・仕様変更 | 02_requirements.md → (必要なら 03/04) → 実装 → テスト |
| 方向転換(ターゲット・コンセプト変更) | 01 から見直し。/pipeline のやり直しを提案 |

影響するファイル・要件ID・画面・テストケースを列挙し、作業計画をユーザーに提示する。破壊的な変更(データ形式の変更等)が含まれる場合は必ず確認を取る。

### 2. 上流ドキュメントの更新

- 仕様変更: `docs/02_requirements.md` を更新(要件の追加・修正、バージョン番号を1.1→1.2のように増分し、末尾に変更履歴を追記)
- デザイン変更: `docs/03_ui_design.md` を更新(トークン変更ならCSS変数定義も)
- 設計に影響する場合: `docs/04_architecture.md` を更新

### 3. 実装(implementer サブエージェントに委譲)

更新後のドキュメントパスと変更内容を渡して実装させる。実装ルールは通常の実装フェーズと同じ(`.claude/skills/implement/references/implementation-guidelines.md` に従う)。

### 4. レビュー(変更規模に応じて)

- コード変更が大きい場合(目安: 3ファイル以上 or ロジック変更): code-reviewer でレビュー
- 見た目が変わる場合: design-reviewer でスクリーンショット確認

### 5. 回帰テスト

1. 変更に対応するテストを追加・修正する(test-engineer に委譲。バグ修正の場合は**再発防止テストを必ず追加**)
2. **既存テストを全部実行する**(`npm test` と `npm run test:e2e`)
3. 既存テストが落ちた場合: 意図した仕様変更による失敗ならテストを新仕様に更新、意図しない失敗なら実装を修正

### 6. ドキュメント整合の最終確認と完了報告

- `docs/05_test_plan.md` に追加したテストケースを追記する
- `docs/06_test_report.md` を回帰テストの最新実行結果で更新する(実行日と対象バージョンを明記。古い結果のまま残さない)
- ユーザーに報告: 変更内容 / 更新したドキュメント / テスト結果(回帰含む) / 影響を受けた既存機能
