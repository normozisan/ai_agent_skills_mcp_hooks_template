# SaaS開発ガイドライン(認証・決済・サーバーサイドDB)

認証(アカウント・ログイン)、決済、サーバー保存データのいずれかを含むアプリを作る場合の追加規約。要求仕様・設計・実装・テスト・リリースの全フェーズで適用する。

## 0. 適用判定

要求仕様に以下のいずれかが含まれたら、このガイドラインを適用する(requirements フェーズで判定し、仕様書に「SaaSガイドライン適用」と明記する):

- ユーザー登録・ログインがある
- 課金・決済がある
- ユーザーのデータをサーバー側(DB)に保存する
- 複数ユーザー/組織でデータを分離する必要がある

## 1. 大原則(違反したら設計レビュー不合格)

1. **認証を自作しない。** パスワードのハッシュ化・セッション管理・トークン発行を自前実装せず、マネージドサービス(Supabase Auth / Firebase Auth / Clerk)または実績あるライブラリ(Auth.js)を使う。
2. **カード情報に触れない。** カード番号を自分のサーバー・DB・ログに通さない(PCI DSSの対象になる)。Stripe Checkout / Payment Links のようなホスト型決済ページを使い、決済情報は決済事業者側だけに持たせる。
3. **認可はサーバー側で必ず検証する。** クライアント側の「ボタンを隠す」はUI演出であって認可ではない。すべてのAPI・DBアクセスで「このユーザーがこのデータに触ってよいか」をサーバー側で検証する。
4. **シークレットをコードに書かない。** APIキー・DB接続文字列は環境変数(`.env`、コミット禁止)で管理し、クライアントに露出するキーと秘密キーを明確に区別する。

## 2. SaaS向け技術スタック既定値

| 領域 | 既定 | 理由 |
|---|---|---|
| フレームワーク | Next.js(App Router)または Vite + Hono(API分離型) | SSR/APIルート、エコシステム |
| 認証 | Supabase Auth(代替: Clerk, Firebase Auth) | マネージド、RLSと統合 |
| DB | Supabase(PostgreSQL + Row Level Security) | RLSでテナント分離をDB層で強制できる |
| 決済 | Stripe(Checkout + Billing + Webhook) | ホスト型でカード非接触、サブスク管理 |
| メール送信 | Resend / SendGrid | 認証メール・通知 |

変更する場合は設計書に理由を明記する。ライブラリの最新の使い方は Context7 MCP で確認する。

## 3. 認証・認可チェックリスト

- [ ] サインアップ/ログイン/ログアウト/パスワードリセット/メール確認のフローが仕様に定義されている
- [ ] セッションの有効期限と更新方法が決まっている
- [ ] 認証エンドポイントにレート制限(総当たり対策)がある
- [ ] 認可がサーバー側(APIミドルウェア or RLS)で実装されている
- [ ] **IDOR対策**: URLやIDを書き換えても他人のデータに到達できないことをテストで検証している
- [ ] 権限ロール(admin / member 等)が必要なら仕様に定義され、昇格経路が保護されている
- [ ] ログにパスワード・トークン・個人情報を出力していない

## 4. 決済チェックリスト

- [ ] 決済フローはホスト型(Stripe Checkout等)で、自サーバーはカード情報を扱わない
- [ ] **Webhookで決済状態を同期**している(成功画面へのリダイレクトだけで課金確定と見なさない)
- [ ] Webhookは署名検証をしている(なりすまし対策)
- [ ] Webhook処理は冪等(同じイベントが2回来ても二重付与されない)
- [ ] サブスクの全状態(trial / active / past_due / canceled)の挙動が仕様に定義されている
- [ ] 解約・返金・プラン変更のフローが仕様に定義されている
- [ ] 開発・テストはStripeテストモード+テストカードで行い、本番キーとテストキーの取り違え防止策がある(環境変数の分離)

## 5. データ設計・マルチテナント

- 全テーブルに所有者(user_id / org_id)を持たせ、**RLSポリシーでテナント分離をDB層で強制**する(アプリコードのWHERE句だけに頼らない)
- 個人情報は必要最小限だけ保存する(取る理由を仕様に書けないデータは取らない)
- 削除要求(退会)でユーザーデータを削除できる設計にする(論理削除/物理削除の方針を決める)
- バックアップとリストア手順をリリースノートに明記する

## 6. 要求仕様フェーズでの追加検討事項(requirements-engineer向け)

SaaS適用時は非機能要件に以下を必ず含める(不要なら「対象外」と理由を明記):

- 利用規約・プライバシーポリシーのページ(課金があるなら**特定商取引法に基づく表記**も。日本で課金する場合は必須)
- 退会とデータ削除のフロー
- メール到達性(認証メールが届くこと)
- 料金プランと課金モデル(月額/年額/従量、無料枠、トライアル)
- 障害時の扱い(決済失敗時のリトライ、サービス停止時の告知)

## 7. テストフェーズでの追加観点(test-engineer向け)

- **認可テストを最優先で書く**: 別ユーザーのデータID・URLへのアクセスが403/404になること(E2E)
- 未ログイン状態で保護ページ・APIに到達できないこと
- Webhookハンドラのユニットテスト(正常イベント/署名不正/重複イベント)
- 決済E2EはStripeテストモードで主要フロー(購入→反映、解約→停止)を1周
- セッション期限切れ後の挙動

## 8. リリースフェーズでの追加チェック(release向け)

- [ ] 本番用シークレットがテスト用と分離され、本番環境にのみ設定されている
- [ ] Webhookエンドポイントが本番URLで決済事業者に登録されている
- [ ] 全ページ・APIがHTTPS
- [ ] RLSが全テーブルで有効(無効のテーブルがないことを確認するクエリを実行)
- [ ] 利用規約・プライバシーポリシー・特商法表記(課金時)が公開されている
- [ ] エラー監視(Sentry等)またはログ確認手段が用意されている
