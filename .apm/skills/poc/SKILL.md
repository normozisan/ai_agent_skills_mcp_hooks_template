# POC試作フェーズ

目的は**仮説検証**。完璧な品質ではなく「動くものを最速で作って試せる状態にする」ことを優先する。成果物は `app/` の動くプロトタイプと `docs/poc/` の最小ドキュメント。

入力: **$ARGUMENTS**

## モード判定

- `--spec` がある場合(または $ARGUMENTS が具体的な仕様書・ファイルパスの場合): **仕様持ち込みモード** — 調査をスキップし、渡された仕様から開始する
- アイデアだけの場合: **調査込みモード** — 軽量調査をしてから作る
- 入力が空ならユーザーに確認する

## POCの品質ライン(本番との違いを明確に)

**やる**: ビルドが通る / 主要フロー(ハッピーパス)が動く / design-guidelines.md セクション1のアンチパターン回避(AIっぽい見た目にしない)/ 明らかな操作不能バグの修正
**やらない**(本番昇格時にやる): 網羅的テスト / 境界値・異常系の作り込み / コードレビュー2周 / デザインレビュー3周 / 詳細な非機能要件

この割り切りを最初にユーザーに一言伝える。

## 手順

### 1. (調査込みモードのみ)軽量調査

market-analyst サブエージェント**1体**に以下をタイムボックス付きで委譲する: 「類似サービス2〜3個の概要・コア機能と、ターゲットの主要ニーズだけを調査。詳細な市場規模やトレンド分析は不要」。結果は次ステップの仕様に直接反映する(独立レポートは作らない)。

### 2. POC仕様の作成(1ページ)

`docs/poc/00_poc_spec.md` に以下だけを書く(要求仕様書のフル形式は使わない):

- **検証したい仮説**(1〜3個。例: 「3タップで記録できれば続けてもらえる」)
- **Must機能(5個以内)** — それぞれ1行の完了条件付き
- **画面(3画面以内)**
- **やらないことリスト**
- 技術スタック(CLAUDE.mdの既定値。変更時のみ明記)

仕様持ち込みモードでは、まず**渡された仕様の原文を `docs/poc/original_spec.md` にそのまま保存する**(本番昇格時に /promote が正式仕様の一次入力として使うため。要約で情報を失わない)。そのうえで、この形式に**要約**する(全機能ではなく検証に必要なMustだけ抽出。POCで削った機能は「やらないことリスト」に記録し、原文に全量が残っていることを明記)。仕様に不明点があれば、ユーザーに選択肢を提示して確認する(些細な点は仮置きして仕様に明記)。仕様をユーザーに1画面で提示し、OKをもらってから実装に進む。

### 3. デザイン(簡易版 — /design は使わない)

アートディレクション3案の比較はしない。design スキル内の `references/design-guidelines.md` を読み、アプリの性格に合うトークン一式(フォント1ペア・カラー・余白)を**自分で1案決めて** `docs/poc/00_poc_spec.md` に追記する。アンチパターン(紫グラデ等)の回避は必須。

### 4. 実装

implementer サブエージェントに POC仕様とデザイントークンを渡して実装させる(小規模なら自分で実装してもよい)。プロジェクト初期化は非対話モード(`npm create vite@latest app -- --template react-ts` 等)。実装ルールのうち **セキュリティと「エラーを黙って握りつぶさない」だけは POC でも守る**(implementation-guidelines.md セクション1のセキュリティ項目)。

### 5. スモーク確認

- `npm run build` が通ること
- Playwright MCP で主要フローを1周実際に操作し、スクリーンショットで見た目のアンチパターン違反がないか確認(正式なデザインレビューはしない)
- 壊れていたら直す(最大2周)

### 6. POCレポートと完了報告

`docs/poc/01_poc_report.md` に保存: 作ったもの / 検証したい仮説と試し方 / 割り切った点(未実装・既知の粗)/ 本番化する場合の推奨事項。

ユーザーに報告: 起動方法(`app` フォルダで `npm run dev`)/ 仮説の試し方 / **本番化するときは `/promote` を実行すればよいこと**。
