# 要求仕様品質ガイドライン

requirements-engineer と要求仕様フェーズが従う品質基準。目的は「実装もテストもできない曖昧な仕様書」を排除すること。

## 1. 不合格条件チェックリスト

以下に1つでも該当したら仕様は不合格とする。

- [ ] **曖昧語**が要件に残っている: 「使いやすい」「高速」「適切に」「わかりやすく」「柔軟に」「できるだけ」「必要に応じて」
- [ ] 受け入れ基準のない Must 要件がある
- [ ] 受け入れ基準がテスト手順に変換できない(Given/When/Then の各要素が具体的でない)
- [ ] 市場調査と接続していない要件が Must に混ざっている(誰のどのニーズか説明できない)
- [ ] MVPスコープが肥大化している(Must が15個を超えていたら疑う)
- [ ] 「やらないこと(Won't)」が書かれていない
- [ ] エラー・例外時の振る舞いが一切定義されていない(正常系だけの仕様)
- [ ] データの制約(最大長、必須/任意、型、件数上限)が未定義

## 2. 良い要件の書き方

- **悪い**: 「素早く記録できること」
- **良い**: 「アプリ起動から記録完了まで3操作以内で完了できること」
- **悪い**: 「大量のデータでも動くこと」
- **良い**: 「1,000件のデータ登録時でも一覧表示が2秒以内に完了すること」

書き方の型(どちらかを使う):
- ユーザーストーリー + 受け入れ基準: 「〈ペルソナ〉として、〈目的〉のために、〈機能〉がほしい」+ Given/When/Then
- 状態駆動(EARS風): 「〈条件/状態〉のとき、システムは〈応答〉すること」

## 3. 優先度付け(MoSCoW)の原則

- **Must** = それが無いとプロダクトの核となる価値検証ができないもの。「あったほうがいい」はMustではない
- 迷ったら Should に落とす。MVPは削るほど良い
- Won't は「今回やらない」の宣言であり、理由を書く(スコープ膨張の防波堤)
- 各 Must が市場調査の「MVPで検証すべき仮説」のどれかに対応しているか確認する

## 4. 非機能要件の最低ライン

以下は毎回必ず検討する(不要なら「対象外」と明記):
性能(表示速度・操作応答)/ 対応環境(ブラウザ・画面幅)/ データ永続化と消失時の扱い / 入力バリデーション / アクセシビリティ(キーボード操作・コントラスト)/ オフライン時の挙動

## 5. セルフレビュー手順(仕様完成前に必ず実施)

1. 全 Must 要件を1つずつ「これのテストケースを今すぐ書けるか?」と自問する。書けなければ書き直す
2. 曖昧語検索: 仕様書内を「使いやす」「適切」「高速」「柔軟」「わかりやす」で検索して置換する
3. ペルソナの視点で主要フローを頭の中で通し、要件の抜け(戻る操作、編集、削除、0件時)を探す
4. MVPを「1〜2日で実装できるか」で見積もり、超えるなら Must を削る
